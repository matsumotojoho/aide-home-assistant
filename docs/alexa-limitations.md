# Alexa Custom Skill の制約 (Phase 2実装前に公式ドキュメントで要再確認)

> **注意**: Alexaの仕様は変更されることがある。Phase 2着手時に必ず公式ドキュメント
> (Alexa Skills Kit / Custom Skill / ja-JP) で以下を再確認し、本ファイルを更新すること。
> 非公式ハック (任意発話の常時横取り、非公式API) は使用しない。

## 設計方針 (仕様書3)

- AlexaはAI本体ではなく「耳と口」。判断・記憶・実行管理はAide Backend
- Alexa標準の高速スマートホーム操作 (「アレクサ、電気つけて」→ Alexa標準スマートホーム) は無理にAI経由にしない
- Aide Skillは「アレクサ、AIを開いて〜」で起動し、セッション継続で連続会話する

## 既知の制約 (2026年時点の理解 / 要検証)

### 起動・呼び出し
- Custom Skillは**ウェイクワード+Invocation Name**が必須。任意の発話を無条件に横取りすることはできない
- Invocation Name (ja-JP) の制約: ひらがな/カタカナ表記推奨、2語以上推奨、「アレクサ」等の予約語・ブランド名不可、起動詞 (「開いて」「起動して」等) を含められない
- 候補: 「エーアイ」「アシスタント」など。実機で認識率を検証して決める
- ワンショット起動 (「アレクサ、<スキル名>で今日19時に帰ると伝えて」) はインテントスキーマ次第で可能

### 会話継続
- 応答で `shouldEndSession: false` を返すとセッション維持 → ユーザーは「アレクサ」なしで続けて話せる
- ただし**無応答が約8秒**で reprompt → さらに無応答でセッション終了。常時聞き続けることはできない
- 長い沈黙をまたぐ会話は「アレクサ、AIを開いて」で再開する運用

### 自由発話の取得
- 完全な自由文取得は `AMAZON.SearchQuery` 等のスロットで近似する (ja-JPでの挙動は要検証)
- インテントに一致しない発話はフォールバックインテントで受ける
- 発話全文が常に取れるとは限らない前提でBackend側を設計する (取れた文字列をそのまま/api/chat相当へ渡す)

### 応答
- 応答はSSML/テキスト。応答生成に時間がかかる場合、**リクエストタイムアウト約8秒**以内に返す必要がある
  → Claude判断が長引く場合は「確認して後で通知します」と即答し、結果はWeb Pushへ回すパターンを実装する
- Progressive Response (処理中の暫定応答) が使える

### その他
- リクエスト署名検証 (証明書チェーン+タイムスタンプ) の実装が必須 (自前HTTPSエンドポイントの場合)
- エンドポイントは有効な証明書のHTTPS (RailwayでOK)
- Account Linking (OAuth) でAlexaユーザーとAideユーザーを紐付け可能。単一ユーザーのPhase 2では簡易マッピング (deviceId/userId固定) から始めてよい
- 無料でスキルを自分用に公開せず開発モードのまま使える

## Phase 2 実装計画

1. ASKコンソールでCustom Skill作成 (ja-JP、Invocation Name実機検証)
2. エンドポイント: Railwayの `/api/alexa` (署名検証ミドルウェア追加)
3. インテント: 自由文キャッチ (SearchQueryスロット) + ストップ系標準インテント
4. `shouldEndSession:false` でマルチターン。会話履歴はBackendの conversations (source=alexa)
5. `alexa.verbosity` 設定 (短く/標準/詳しく/全文) に応じてspeak文を要約
6. 8秒以内に返せない処理は即時応答+Web Push通知へ
